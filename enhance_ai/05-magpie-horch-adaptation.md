# Magpie-Horch：外置 Fable 式工程 Skill 架构

> 状态：第一版已安装到用户级 Codex Skill 目录；`/Users/lute/project/Magpie-Horch` 未新增、修改或接线任何文件。
> 目标：让当前选用的 LLM 在这个复杂 DSH/LUTE 工程中呈现更强的任务分解、上下文恢复、因果诊断、独立复核与证据交付能力，而不是把长系统提示词、外部插件或工程状态写进项目本体。

## 一、先校准目标：不是“复制 Fable 模型”，而是复制可迁移的工作机制

Skill 可以显著提升当前模型的**工作可靠性**：更早发现边界、少做无关改动、更准确恢复断点、把测试/运行/交付分开、对完成结论给出证据。它不能把基础模型的知识广度、上下文窗口、工具权限或原生推理上限变成另一个模型，因此不承诺“等价于 Fable 5.1”。

这里采用的定义是：让当前 LLM 在工程行为上具备“Fable 式”的五个外显能力。

| 外显能力 | 从资源萃取的方法 | 在 Magpie-Horch 的具体落点 |
| --- | --- | --- |
| 复杂任务编排 | `fable-method`、`fable-advisor`、`fable-foreman` 的任务契约、角色分离、写入集 | 结果/禁区/消费链/验收门/回滚组成的紧凑任务契约 |
| 真实状态恢复 | `FableClaudeMDForOpus`、`fable-mode` 的基线/恢复账本 | 从 `AGENTS.md`、git、目标状态和实际载荷读取；不从旧聊天猜进度 |
| 因果诊断 | `fablize`、`value-for-fable` 的复现、反证、消融与低成本区分实验 | 先证据链再窄修复；把临时缓解与根因修复分开 |
| 独立质量裁决 | `fusion-fable` 的独立 judge、`fable-mode` 的三态结论 | 用 `PASS / FAIL / UNVERIFIABLE` 审查源码、门禁、装载和运行态 |
| 清晰边界的 Skill 体系 | `claude-directory` 与 `emilkowalski/skills` 的单一决策类 Skill | 不建立“万能 Fable 提示词”，而是按开发生命周期拆成四个窄 Skill |

上表只使用已完成的仓库档案与方法原子，见 [仓库档案](01-repository-dossiers.md) 与 [方法原子](02-method-atoms.md)。没有复制未获授权的系统提示词、无许可证仓库文本、hook、外部模型调用脚本或“绕过批准”的命令。

## 二、为什么这套结构适合 Magpie-Horch

该项目不是普通单应用仓库：它有受 pin 约束的 DSH 基座、五类 package、`file:` 多副本装载链、宿主注入、用户级 profile、运行态 UI、DMG 交付和大量已经发生过的故障模式。项目自身规则已经明确：

- 基座是只读 pin；
- `pnpm run gate` / `gate:full` / `gate:strict` 是不同强度的证据门；
- 磁盘、安装源、装载点、运行中的实例是不同事实；
- 空射程、历史绿灯、单一日志、单次重试、只看退出码都可能是假绿；
- 共享脏工作区中的读数必须有 owner，不能把别人的改动或仪器问题归因成产品缺陷。

因此，最不适合它的方案是一个全局、长篇、永远强制多代理的“Fable prompt”。那会与现有 `AGENTS.md`、故障账本和门禁平行造规则，既污染上下文又增加假绿风险。第一版把项目现有机制当作权威，把 Skill 设计成**什么时候该采用哪种工程行为**的外置路由层。

## 三、已安装的四个原子 Skill

| Skill | 解决的场景/问题 | 输出 | 触发边界 |
| --- | --- | --- | --- |
| `magpie-horch-feature-delivery` | 新功能、跨包改动、运行时/打包/发布相关实现容易失控 | 最小写入集、任务契约、实现与分层验收 | 只在 Magpie-Horch 功能交付时使用 |
| `magpie-horch-evidence-review` | “写了/测试绿了”被误称为“完成” | 独立的命题—证据—裁决表 | 审查、验收、完成前复核、发布判断 |
| `magpie-horch-incident-diagnosis` | 白屏、卡死、加载失败、性能回归被靠猜或加超时处理 | 可反驳的根因链、窄修复和前后验证 | 诊断或修复 bug/事故 |
| `magpie-horch-context-recovery` | 长会话、多任务、脏工作区下从错误断点继续 | 真实状态快照与唯一下一步 | “继续/恢复/断点/状态/下一步” |

它们都在用户级目录 `~/.codex/skills/` 中；每个都有 Magpie-Horch 的 scope guard。它们不会修改以下项目面：

- `AGENTS.md`、`CLAUDE.md`、项目 `.codex/` 配置或 goals；
- source、package、profile、vendor、presets、门禁、DMG 或 git 状态；
- 外部模型、第三方 API、凭证或企业数据。

项目内仍由现有 `AGENTS.md`、ADR、门禁和用户授权决定“能不能做”；外置 Skill 只帮助模型在该规则下“怎样做得更可靠”。

## 四、运行关系

```text
用户请求
  │
  ├─ 继续 / 当前状态 ───────────────→ context-recovery
  │                                      │
  ├─ bug / 卡死 / 白屏 / 根因 ───────→ incident-diagnosis
  │                                      │
  └─ 新功能 / 改动 / 重构 ───────────→ feature-delivery
                                         │
                                  完成前 / 审查 / 发布判断
                                         │
                                         └──────────────→ evidence-review
```

同一项复杂交付可以顺序使用多个 Skill，但不要让它们变成四套独立账本：任务事实仍住在项目已有的权威文件、源代码、测试和运行读数里。Skill 不默认创建项目内 ledger；只有用户要求固化决策时，才按项目 Note/ADR 规范写入。

## 五、迁移与验证节奏

### Phase 1：当前已完成 — 外置安装与静态校验

四个 Skill 已按用户级安装，不污染 Magpie-Horch。下一步先在真实开发任务中使用，而不是人工改动项目来“演示”。每次选一个符合场景的真实任务，检查：

1. 是否正确触发而没有干扰小改；
2. 是否在写入前明确了最小写入集和不可触碰边界；
3. 是否把源码、门禁、装载和运行态分开报告；
4. 是否在无法观察时保留 `UNVERIFIABLE`，而不是造一个完成结论；
5. 是否减少返工、错误续跑或无法解释的测试结果。

**触发注册已验证（2026-09-23）**：四个名称已出现在当前 Codex 会话的 Available skills 清单中，说明 `~/.codex/skills/` 的发现链已生效；四份 `SKILL.md` 都通过 `quick_validate.py`。本轮进一步收紧了它们的前置 description 和相互转交边界，避免以下常见误路由：

| 开发者语句 | 应选 Skill | 不应误选为 |
| --- | --- | --- |
| “继续上次 Magpie-Horch 的工作，先告诉我真实状态” | `magpie-horch-context-recovery` | 直接实现功能 |
| “实现设置页的一个跨包新能力” | `magpie-horch-feature-delivery` | 纯审查或事故诊断 |
| “启动一直卡在 Loading plugins，先定位根因” | `magpie-horch-incident-diagnosis` | 用新功能流程掩盖故障 |
| “这次改动真的完成了吗？不要改代码，只审查” | `magpie-horch-evidence-review` | 自动修复或状态恢复 |

这证明的是**发现、格式和路由契约**；模型在真实自然语言中的最终选择仍应以第一条真实 Magpie-Horch 开发请求作行为验收。若需要显式确认，可在该请求中直接写出 `$magpie-horch-feature-delivery` 等名称；它们保持默认的自动发现策略，并不要求每次手动点名。

**独立前向路由测试已完成（2026-09-23）**：独立只读评估者只读取四份 Skill，以 10 条真实开发者语句进行盲测。初测中，8 条核心工程语句获得单一高置信首选路由；它发现两处关键词误触发风险——纯 README 错别字会被“修改”吸收、纯 TypeScript 风格讨论会被“代码审查”吸收。本轮已将这两项排除条件写入相应 description，并收紧“旧任务但下一步明确”不应进入恢复模式的边界。最终复测显示 10/10 条语句都有明确的预期路由：8 条进入恰当的专项 Skill，README 错别字与纯“是否优雅”讨论均明确为“无专项 Skill”。路由测试不访问网络、不调用外部模型、不修改 Magpie-Horch；它验证的是 Skill 发现与文本路由契约，真实开发请求仍是最终行为验收。

### Phase 2：两到三个真实任务后的 SkillOpt 式迭代

每个 Skill 收集 3–5 个已完成任务作为训练样本，并保留 2 个未参与编辑的 held-out 情景。只允许小而可解释的文本编辑；新的版本必须在 held-out 场景上严格改善，否则回退。评价维度：触发准确性、完成度、步骤成本、边界/安全、输出质量。

这借鉴 `SkillOpt` 的“轨迹 → 反思 → 有界编辑 → held-out 验证门”方法，但不把仓库中已有的历史分数当作这四个新 Skill 的性能证明。

### Phase 3：可选的独立模型裁决层（暂不启用）

当你明确允许某类任务把上下文发送给外部模型，并愿意定义成本、数据分类、日志保留和人工决策权时，再增加一个 `magpie-horch-independent-panel`：它只做设计争议或高风险 diff 的独立只读审查，不能直接写工作区、提交、发布或调用破坏性脚本。此层来自 `fusion-fable` 的“独立候选 + 独立 judge”，但因数据、成本和外部权限边界尚未授权，本次不创建也不调用。

## 六、建议的首个实战入口

下一次你要在 Magpie-Horch 做一个跨包功能、运行时 UI 改动、`file:` 装载相关改动，或需要继续一条旧任务时，直接用自然语言说明目标即可。Skill 会先读取真实状态并选择对应模式。

如果你希望马上做一次可衡量的首轮试运行，最合适的不是碰未解决的启动事故，而是挑一个**边界清楚、可在本地验证、不会触及 pinned vendor 或生产发布**的标准功能任务：它足以同时检验任务契约、最小写入集和独立验收，又不会把 Skill 评估与历史事故排障混在一起。
