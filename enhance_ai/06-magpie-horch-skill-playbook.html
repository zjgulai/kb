Magpie-Horch · 外置开发 Skill

把 AI 当成靠谱开发搭子，而不是会乱冲的自动补全

这份 Playbook 讲清楚四个新增 Skill：什么时候该用、它会帮你做什么、你该怎样说、它又不会越界做什么。你不需要记一套复杂咒语，正常说人话就行。

一句话理解 选哪一个 四个 Skill 怎么串起来 直接这样说 它不会做什么

先用一句话说清楚

不要把它理解成四个机器人。它更像是给同一个 AI 开发搭子准备的四种工作模式：先弄清现实、再找故障、再做功能、最后验收结果。

最简单的判断法：你现在缺的是“真实状态”、需要“找为什么坏了”、要“把明确的东西做出来”，还是要“确认别人说的完成到底是不是真的”？四种缺口，对应四个 Skill。

30 秒选对 Skill

不用猜技术名词，先看你正在面对哪种现实问题。

你不知道现在到底进展到哪了 先把事实捞出来 旧任务、长对话、脏工作区，代码和测试谁留下的都不清楚。先恢复真实状态，再决定做什么。 已经看见一个坏现象 先找根因，不要猜 白屏、卡死、Loading plugins、门禁失败、性能回归。先证明为什么坏，别靠叠补丁或拉长超时。 目标和范围已经清楚 把功能稳稳做出来 新增功能、跨包改动、运行时 UI、file: 装载、测试、打包或交付链路。它会把改动和验证收住。 已有改动或完成声明 确认“真的完成了吗” PR 能否合入、功能是否真生效、发布是否有证据。默认只读，不会为了让结果好看而顺手改代码。

四个 Skill，各自到底管什么

它们之间可以交接，但不会互相抢活。你只要说清自己想要的结果，AI 会优先选择合适的工作模式。

先恢复现实

magpie-horch-context-recovery

它解决的问题：“我上次做到哪了？”“这堆改动是谁的？”“测试是刚跑的还是历史记录？”

你可以这样说 继续昨天的 Magpie-Horch 工作，但我不确定实现、测试和日志分别到哪一步了。先给我真实状态和唯一下一步。

它会帮你产出：一张真实状态快照：目标是否已确认、代码是否已写、测试是否本次运行、运行态是否见过、哪些改动不属于本任务，以及一个最小下一步。

它不会做：不会因为任务来自昨天就自动接着写；也不会 reset、清理、提交或把不明来源的改动算到你头上。

什么时候不要用它
如果你的目标、要改的范围和下一步都已经明确，直接进入功能交付更快。不要为了“看起来谨慎”多走一层恢复流程。
先证明根因

magpie-horch-incident-diagnosis

它解决的问题：看得见问题，但不知道真正卡在哪一层。尤其适合白屏、卡死、插件加载失败、性能回归和宿主兼容问题。

你可以这样说 DSH 启动一直停在 Loading plugins。先复现并定位根因；不要先改超时，也不要靠猜。

它会帮你产出：复现证据、并列假设、最便宜的区分实验、根因或候选根因、窄修复方案与回滚方式。

它不会做：如果你只授权诊断，它会停在证据和方案，不会偷偷修改代码。根因和写入范围明确后，才交给功能交付实施。

Magpie-Horch 的重点提醒
遇到持续加载或卡死，不能因为某次日志、一次重试或延长 watchdog 后暂时能启动，就宣布已修好。需要同时看生命周期、运行载荷、profile/bundle、装载点和用户面。
稳稳把东西做出来

magpie-horch-feature-delivery

它解决的问题：功能实现不只是“改一行代码”。特别是跨包、运行时 UI、file: 依赖、打包和发布链路，最容易出现源码改了但消费者没用上的假完成。

你可以这样说 新增一个任务看板能力，涉及 packages、运行时 UI 和 file: 装载。先确认最小改动范围，再实现并给出真实验证。

它会帮你产出：最小写入集、明确不碰的边界、消费链、验收命题、对应测试或运行读数，以及未能证明的部分。

它不会做：不会把纯 README 文案、错别字或仅审美调整拖进一套复杂交付流程；也不会越过项目规则、用户授权、ADR 或既有门禁。

小改也能用，但会更轻
已知范围的一行代码修复仍可进入功能交付，不过它只需要点明目标文件和直接验证；不会强行写成长篇任务契约。真正跨包或运行时改动，才会展开完整的消费链与完成门。
只看证据，不替人背书

magpie-horch-evidence-review

它解决的问题：“代码写了”“测试绿了”“页面打开了”常被误说成“功能完成”。这个 Skill 专门判断结论是否站得住。

你可以这样说 不要改代码。只读复核这轮 profile sync 改动是否真的生效，以及这个 PR 能不能合入。

它会帮你产出：每条验收命题对应的证据，以及 PASS、FAIL 或 UNVERIFIABLE。不能证明时会明确缺什么，而不是把猜测说成通过。

它不会做：不替实现者顺手修 bug，不把退出码 0、历史绿灯或单条日志当成完整交付；“这段代码优不优雅”也不属于它的专项范围。

它重点查哪几层
它会按需要核对源码和 diff、自动化判据、构建或装载链路、真实运行态或用户面。四层互相补充，任何一层绿都不能替其他层背书。

一个任务常常要串着用，不是只选一次

最典型的复杂问题是：先找清楚为什么坏，再写窄修复，最后独立确认修复是否真的生效。

1. 故障诊断

复现现象，比较竞争假设，证明根因。这里先不靠猜写补丁。

→
2. 功能交付

根因和最小写入范围清楚后，再实现修复、跑针对性验证、检查消费链。

→
3. 证据审查

从结果倒查证据。确认不是“某层绿了”，而是用户真正能用。

如果你连当前 branch、改动归属或上一次验证都说不清，最前面先加一次断点恢复。它不做实现，只把起点校正。

日常开发时，直接这样说就够了

下面这些句子不是固定模板，只是告诉你什么信息最有用。目标、范围、禁止项和“怎样算完成”说得越清楚，AI 越能快速走对路径。

1
你要接着做，但不知道前情

先让 AI 做状态恢复，而不是让它凭聊天记录猜着继续。

继续 Magpie-Horch 上次的设置页任务。先只读核对 branch、已有改动、测试和运行态；告诉我真实状态与唯一下一步，先不要写代码。
2
你要做一个明确的新功能

把用户会得到什么、哪些地方不能碰、怎么证明做完说清楚。

在 Magpie-Horch 新增 X 能力。可以修改 A 和 B，不能动 vendor/dsh-desktop。需要覆盖运行时 UI 和本地 gate；先给最小写入范围，再实施。
3
你看见异常，先想知道为什么

明确告诉 AI 不要先 patch，让它建立可反驳的根因链。

当前出现 X 异常，复现条件是 Y。先定位根因并列出证据、反证和最便宜的区分实验；在我确认前不要修改代码。
4
别人说做完了，你要验收

明确“只读”，把审查和修复的权限分开。

只读审查这轮改动是否真的达到 X。检查 diff、测试、装载/构建和运行态；按 PASS、FAIL、UNVERIFIABLE 给我结论，不要写代码。

如果你想百分百指定某一种工作模式：在请求里直接写 $magpie-horch-feature-delivery、$magpie-horch-incident-diagnosis、$magpie-horch-evidence-review 或 $magpie-horch-context-recovery。大多数时候不需要点名，正常表述场景即可自动发现。

它能帮你提高质量，但不会替你越权

这些 Skill 的价值不是“让 AI 变得很会说”，而是让它在复杂工程里少犯典型错误：错接断点、把症状当根因、源码改了却没生效、测试绿了却没有真正验收。

它会主动帮你守住的事

  • 区分当前事实、历史记录和个人猜测。
  • 保护共享或脏工作区，不擅自 reset、清理或把别人的改动算进本任务。
  • 把源码、构建/装载、运行态和用户面分开验证。
  • 无法证明时明确写 UNVERIFIABLE，不编一个“应该没问题”。
  • 把诊断、实施和独立验收分开，减少“自己证明自己”的假绿。

它不会替你做的事

  • 不会覆盖 AGENTS.md、ADR、项目门禁或你的显式授权。
  • 不会因为“检查一下”就偷偷修改、提交、发布或调用外部系统。
  • 不会把纯文案错别字、代码命名或审美讨论升级成复杂工程流程。
  • 不会把一次退出码为 0、一个日志或历史绿灯当成完整交付。
  • 不会自动把 Magpie-Horch 的项目规则写进仓库；Skill 保持在用户级目录，避免污染项目。

每次开工前，给 AI 四句话就很够用

不必写正式 PRD。下面四点齐了，Skill 就能既快又稳地工作。

我要什么 用户最终应该看见或得到什么。
能碰什么 允许的包、文件或模块；明确不能碰的边界。
眼前有什么 已知故障、已有改动、日志、测试或不确定性。
怎么算完成 测试、界面、运行态或合入标准；没有就说需要一起定义。

推荐先拿一个边界清楚、可在本地验证、不会碰 pinned vendor 或生产发布的标准功能任务做第一轮实战。完成两到三个真实任务后，再根据误触发、返工和验证缺口微调 Skill 文本，而不是一开始就把规则写得越来越长。
